# RogueDuel (가칭) 기획서
로그라이크 덱빌더 × 실시간 PvP 듀얼 — 게임서버 프로그래머 포트폴리오 프로젝트

Document Version: 1.0
Status: Initial Specification (Grilling Session 결과물)
작성 배경: DevGrowth 기획 중 커리어 방향 재검토를 거쳐 도출된 신규 프로젝트

프로젝트명은 가칭입니다. 개발 진행하면서 확정하세요.


==================================================
0. 이 문서가 나온 배경
==================================================

이 프로젝트는 원래 별도로 기획했던 "DevGrowth"(.NET 백엔드 전환용
학습관리 시스템)를 대체하는 프로젝트입니다.

DevGrowth를 설계하는 과정에서 다음이 드러났습니다.

- DevGrowth 스펙의 예시 데이터(경력 1.5년, C# 65점 등)는 실제 본인
  상태가 아닌 가상의 예시였다.

- 실제 스킬 베이스는:
  - Unity: 2024-08 ~ 2025-08, 약 1년 실무 경력 (현재 약 1년 공백)
  - JS/웹: 현재 직무이나 AI 도구 의존(바이브코딩) 위주, 손코딩 경험 적음
  - 백엔드/.NET: 실질적으로 제로

- 순수 백엔드 전환은 제로베이스라 6개월 내 이직 목표에 비해 리스크가
  매우 크고, 순수 유니티 복귀는 가장 안전하지만 "왜 다시 유니티로
  돌아왔는가"에 대한 스토리가 약하다.

- 대신 "유니티 클라이언트 + 백엔드"를 결합한 게임서버/하이브리드
  포지셔닝이 채택되었다. 두 경력을 버리지 않고 합치는 방향이며,
  이 조합을 가진 지원자가 드물어 차별화가 된다.

이 문서는 그 결론을 실제로 실행하기 위한 프로젝트 기획서입니다.


==================================================
1. 프로젝트 개요
==================================================

프로젝트 목적:

"게임서버 프로그래머" 또는 "클라이언트+서버 하이브리드" 포지션으로
이직하기 위한 포트폴리오 프로젝트를 실제로 손으로 설계·구현한다.

핵심 원칙:

만드는 것 자체가 실력 증명이 되어야 한다.
AI나 프레임워크가 핵심 로직을 대신 해결해주면 포트폴리오로서
가치가 없다.


==================================================
2. 커리어 전략 배경
==================================================

목표 포지션:

게임 서버 프로그래머 / 게임 클라이언트-서버 하이브리드 개발자


실제 스킬 베이스 (정직한 현재 상태):

Unity            1년 실무 경력 (2024.08 ~ 2025.08), 현재 공백 약 1년
JavaScript/웹     현재 직무, AI 의존도 높음(바이브코딩), 손코딩 약함
C# 백엔드/.NET    사실상 제로


왜 하이브리드인가:

- 유니티만 하면: 실제 경력이 있지만 1년 공백, 차별화 약함
- 백엔드만 하면: 제로베이스, 6개월 목표에 비해 리스크 과다
- 하이브리드: 기존 유니티 경력을 낭비하지 않으면서, 백엔드까지
  다루는 사람은 드물어 채용 시장에서 차별화됨
- 유니티와 백엔드 모두 C#이라 새 언어를 배울 필요 없이 한 언어를
  깊게 파는 효율이 있음


이직 목표 시점:

6개월 목표, 유동적 (완성이 우선이며 필요시 추가 투자 가능)


시간 예산 (실측값):

평일 가용 시간     90분
주말 가용 시간     180분
주간 합계          810분 (약 13.5시간)
6개월(약 26주) 총합  약 351시간

배분 원칙(Study 20 / Practice 30 / Project 40 / Review 10)에서
Project 몫만 계산하면:

6개월 기준 프로젝트(이 게임) 순수 투입 가능 시간: 약 140시간

140시간은 표준 40시간 근무 기준 3.5주치에 불과합니다.
따라서 콘텐츠 양보다 "핵심 시스템이 실제로 동작하는가"가
훨씬 중요합니다. (19번 섹션 로드맵 참고)


==================================================
3. 핵심 개발 원칙
==================================================

원칙 1. 바이브코딩 금지

AI가 짜준 코드를 이해도 못하고 그대로 쓰지 않는다.
면접에서 "왜 이렇게 짰냐"는 질문에 답할 수 없는 코드는
포트폴리오가 아니다.


원칙 2. AI는 보일러플레이트만, 핵심 로직은 직접 작성

18번 섹션의 경계선을 따른다.


원칙 3. 콘텐츠 양보다 시스템 완성도

카드가 20장이든 100장이든 면접관 눈엔 큰 차이가 없다.
재접속 처리가 허술하거나 서버 검증이 없으면(클라이언트가
치트 가능하면) 핵심 스토리 자체가 무너진다.


원칙 4. 서버 권위(Authoritative Server) 우선

클라이언트는 "의도"만 보내고, 실제 판정은 항상 서버가 한다.
이것이 이 프로젝트가 증명해야 할 가장 중요한 개념이다.


원칙 5. 기성 멀티플레이어 프레임워크(Photon/Mirror/FishNet) 사용 금지

매치메이킹/룸 관리/상태 동기화를 서드파티에 위임하면
정작 증명해야 할 핵심 역량을 남에게 맡기는 셈이 된다.
ASP.NET Core + SignalR로 직접 설계한다.

4. 게임 컨셉
==================================================

장르:

로그라이크 덱빌더 + 1:1 턴제 PvP 듀얼

레퍼런스:

Slay the Spire류의 로그라이크 덱빌딩 구조를,
몬스터가 아닌 실제 플레이어와의 PvP 대결에 적용한 형태


왜 이 장르인가 (이전 논의 요약):

- 싱글플레이+리더보드만으로는 "리더보드 CRUD API" 수준이라
  게임서버 역량 증명이 안 됨 → 기각
- 실시간 액션 넷코드(예측/재조정, UDP)는 6개월 내 시니어 엔지니어도
  어려워하는 영역 → 기각
- 턴제 PvP는 동시 이동/물리 동기화 문제가 없어 다루기 쉬우면서도,
  매치메이킹/룸 상태관리/서버 검증이라는 핵심 스토리를 정확히
  보여줄 수 있음 → 채택


핵심 루프:

로그라이크 런 진행 (카드 획득, 덱 구성, 노드맵 이동)
      |
      v
매치메이킹 (상대 탐색)
      |
      v
턴제 PvP 듀얼 (서버 검증 기반 실시간 턴 교환)
      |
      v
결과 반영 (승패, 레이팅, 매치 기록)
      |
      v
다음 런 진행 or 재도전

9. 매치메이킹 설계
==================================================

MVP (Phase 1):

단순 FIFO 대기열.
대기열에 들어온 순서대로 2명씩 묶어서 매치 생성.


Stretch (Phase 2):

ELO 기반 레이팅 매칭.
레이팅 차이가 일정 범위 안에 드는 상대를 우선 매칭하고,
대기 시간이 길어지면 범위를 점진적으로 넓힘.


핵심 설계 포인트 (직접 구현 대상):

- 대기열 등록/취소 처리 (플레이어가 매칭 도중 이탈하는 경우)
- 동시에 여러 플레이어가 대기열에 진입할 때의 동시성 처리
  (락 또는 원자적 큐 연산)
- 매치 성사 시 RoomId 발급 및 양쪽 클라이언트에 통지

10. 룸/세션 상태머신
==================================================

상태 정의:

Waiting        매치 성사 후 양쪽 클라이언트의 Hub 연결 대기
InProgress     듀얼 진행 중 (턴 루프)
Reconnecting   한쪽 플레이어 연결 끊김, 재접속 대기
Completed      정상 종료 (승패 결정)
Abandoned      한쪽이 타임아웃/재접속 실패로 몰수패 처리


상태 전이 규칙 (직접 구현 대상 - 이 프로젝트의 핵심):

Waiting
  -> 양쪽 연결 완료 시 InProgress로 전이
  -> 일정 시간 내 미접속 시 Abandoned

InProgress
  -> 턴마다 TurnDeadline 설정, 시간 초과 시 자동 패스 또는 패널티
  -> 한쪽 연결 끊김 감지 시 Reconnecting으로 전이
  -> 승패 조건 충족 시 Completed로 전이

Reconnecting
  -> 일정 시간 내 재접속 시 InProgress로 복귀 (현재 상태 스냅샷 재전송)
  -> 시간 초과 시 Abandoned (남은 플레이어 승리 처리)

Completed / Abandoned
  -> MatchHistory 저장, 룸 정리(메모리 해제)


이 상태머신이 실제로 이 프로젝트에서 "게임서버 개발자"라는
포지셔닝을 증명하는 핵심 산출물입니다. 면접에서 가장 깊게
설명할 수 있어야 하는 부분입니다.

11. 서버 권위 검증 (Authoritative Server)
==================================================

원칙:

클라이언트는 판정하지 않는다. 클라이언트는 "의도"만 서버에 보내고,
서버가 검증한 결과만 신뢰한다.


클라이언트 -> 서버 (의도 예시):

{
  "type": "PlayCardIntent",
  "roomId": "GUID",
  "cardInstanceId": "GUID",
  "targetPlayerId": "GUID"
}


서버 검증 절차 (직접 구현 대상):

1. 현재 턴 소유자가 맞는지 확인
2. 해당 카드가 실제로 플레이어 손패에 있는지 확인
3. 자원(마나)이 충분한지 확인
4. 카드 효과 적용 (데미지/방어/상태이상 등)
5. 양쪽 플레이어 상태 갱신 후 브로드캐스트


서버 -> 양쪽 클라이언트 (결과 브로드캐스트 예시):

{
  "type": "GameStateUpdate",
  "roomId": "GUID",
  "playerA": { "hp": 42, "resource": 1, "hand": [...] },
  "playerB": { "hp": 35, "resource": 2, "hand": [...] },
  "turnOwner": "GUID",
  "turnDeadline": "2026-08-11T12:00:00Z"
}

핸드 정보는 각 클라이언트에게 본인 것만 전체 공개, 상대 것은
장수만 공개하는 등 정보 비대칭 처리도 서버 책임이다.


==================================================
12. 카드 효과 시스템 설계
==================================================

MVP 범위: 카드 20~30장, 효과 타입 5~7종 정도로 제한

효과 타입 예시:

Damage         상대 HP 감소
Block          자신 방어막 획득
Draw           카드 추가로 뽑기
GainResource   자원 획득
ApplyStatus    상태이상 부여 (예: 취약, 힘 증가)


설계 방향:

카드 데이터는 서버와 클라이언트 양쪽에서 동일한 정의를 참조해야
판정 불일치가 없다. MVP에서는 카드 정의를 JSON/DB에 저장하고
서버가 단일 진실 공급원(source of truth) 역할을 하며,
클라이언트는 표시(연출)만 담당한다.

==================================================

GameStateUpdate(state)
TurnTimeout(playerId)
MatchEnded(winnerId, reason)

15. 데이터베이스 스키마 개요
==================================================

Users               (Id, Email, PasswordHash, Nickname, Rating)
Cards               (Id, Name, Cost, EffectType, EffectValue)
RunStates           (Id, UserId, NodeMapProgress, CurrentDeck, Status)
MatchHistories      (Id, RoomId, PlayerAId, PlayerBId, WinnerId, CreatedAt)
LeaderboardEntries  (UserId, Rating, Wins, Losses, UpdatedAt)

MatchRoom, PlayerDeckState는 매치 진행 중에만 필요한 런타임 상태이므로

매치 종료 시 요약 결과만 MatchHistories에 영속화한다.
